# 企业级项目设计与知识运营闭环

## 1. 设计目标

电商客服中台不是单一问答机器人，而是可信知识服务平台：对稳定政策问题给出有来源的回答，对订单和物流使用实时业务服务，对退款等高风险动作要求用户确认、幂等和审计，对投诉和不确定问题交给人工处理。

## 2. 业务到技术映射

| 业务问题 | 项目设计 | 关键边界 |
|---|---|---|
| 复合咨询 | Gateway -> Manager -> Domain Agent，结构化拆解并行执行 | Manager 不直接执行写操作 |
| 政策问答 | Milvus Dense + BM25 + Reranker | 只使用当前有效版本并返回引用 |
| 业务查询 | Order/Product/Logistics/Coupon MCP | 实时事实以业务服务为准 |
| 退款和高风险操作 | 草案 -> 确认 -> 幂等执行 -> 审计 | 模型不能决定身份、金额和状态变更 |
| 高频 FAQ | 按租户、版本和可见范围隔离的 Redis 语义缓存 | 不缓存订单、物流、价格、库存、退款状态 |
| 知识更新 | 审核、独立 Collection、评测、灰度、回滚 | LLM 只能生成候选，不能自动发布规则 |

## 3. 领域职责

| 领域 | 职责 | 工具边界 |
|---|---|---|
| Order | 订单状态、售后资格、退款草案 | 不能绕过服务端校验直接写库 |
| Product | 商品说明、规格、静态信息 | 实时价格/库存需调用业务服务 |
| Logistics | 轨迹、异常和预计送达 | 只读，不修改履约状态 |
| Coupon | 可用券和门槛判断 | 不直接发券或核销 |
| Policy | 政策、SOP、FAQ 检索和引用 | 不用模型记忆替代知识库 |

## 4. 身份、权限和多租户

1. API 层验证 JWT/OIDC 令牌，生成可信的 `tenant_id`、`user_id`、角色和可见范围。
2. URL 中的 `user_id` 仅用于与认证主体一致性校验，不能作为可信身份来源。
3. Manager 只处理业务内容和结构化计划；领域 Agent 只能看到白名单工具。
4. MCP Server 运行时注入身份，并再次校验租户和资源归属。
5. 知识检索、缓存、对话、工单和审计均按租户隔离；敏感字段脱敏后才能进入日志和 Trace。

RBAC 用于粗粒度角色控制，ABAC 用于租户、资源归属、知识可见范围、操作风险和环境等属性判断。二者共同形成访问控制，不把权限判断交给模型。

## 5. 受控退款流程

```text
用户请求退款
  -> 查询订单和退款资格
  -> 生成退款草案
  -> 展示金额、订单、原因和影响
  -> 用户确认并提交确认令牌
  -> 服务端校验令牌、权限、订单状态和幂等键
  -> 订单域服务执行条件更新
  -> 写入退款命令和审计事件
  -> 返回处理中/成功/失败
```

确认令牌至少绑定草案、租户、用户、订单、金额、有效期和版本。幂等键降低重复提交风险，但最终资金一致性还依赖订单服务、支付渠道和对账系统。

## 6. 知识运营闭环

```text
聊天、工单、录音等交互数据
 -> 脱敏、转写、聚类和质量筛选
 -> 候选 FAQ、知识片段、实体关系或规则
 -> 业务/运营/法务人工审核
 -> 新版本离线建库
 -> 检索、引用、拒答和权限回归
 -> 灰度发布到当前知识版本
 -> 观察命中率、MRR、无引用率、转人工率、延迟和反馈
 -> 回流未解决问题，补全知识缺口
```

知识图谱可以用于实体、关系、规则和影响分析；但当前项目对外的核心实现口径是版本化混合检索和 MCP 受控工具，不能把尚未落地的图数据库写成既成事实。

## 7. 工具网关与工程化

MCP 统一工具 Schema、身份注入、参数校验、白名单、超时、限流、幂等和审计。工具服务与业务数据源解耦，未来可从本地 SQLite Mock 替换为订单、商品、物流和营销领域服务，不改变 Agent 的能力边界。

架构应支持：

- 多副本无状态 Manager 和可恢复的 Redis checkpoint。
- PostgreSQL 工单、退款命令、确认令牌和审计事件的事务存储。
- Milvus 独立 Collection 的知识发布和快速回滚。
- Prometheus 指标、Langfuse Trace、脱敏、采样和保留期控制。
- Prompt、工具 Schema 和知识版本的 CI 回归，避免供应商或模型锁定。

## 8. 质量与验收

| 维度 | 验收方式 |
|---|---|
| 路由 | 170 条固定标注集，统计领域、意图、工具和转人工是否全对 |
| 检索 | 100 条固定政策集，比较 Hit@3、MRR，并做三组消融 |
| 安全 | 越权、提示注入、伪造身份、重复退款和未确认写操作测试 |
| 版本 | 新版本先评测再激活，故障时切回旧 Collection |
| 性能 | 固定 FAQ 对照压测统计缓存命中 P95 和 Token 口径 |
| 运营 | 观察无引用率、误转/漏转人工、重复工单、工具失败率和用户反馈 |

## 9. 迭代阶段

1. 建立 Gateway 鉴权、租户上下文、工具白名单和高风险确认边界。
2. 建立 Dense+BM25+Reranker、引用、拒答和版本化发布链路。
3. 建立聊天/工单脱敏、问题聚类、候选知识审核和回归评测。
4. 建立看板、Trace、压测、反馈回流和图谱/规则分析能力。
