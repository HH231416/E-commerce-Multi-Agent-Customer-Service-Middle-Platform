# 混合检索与知识版本设计

## 1. 目标与边界

RAG 负责政策、售后规则、客服 SOP 和 FAQ 的知识问答，不负责读取实时订单、物流、价格、库存或退款状态。后者必须通过 MCP 查询业务服务。RAG 的职责是找出当前有效、用户有权访问且可引用的证据，再由模型基于证据组织回答；证据不足时拒答、追问或转人工，不能用模型记忆补全政策。

生产主链路统一为：

```text
用户问题
 -> 租户/可见范围/知识版本校验
 -> Dense + BM25 双路召回
 -> Milvus WeightedRanker 融合
 -> Top25 粗排截断
 -> BGE Reranker 精排
 -> Top3 证据、来源和版本
 -> 受约束生成 / 拒答 / 转人工
```

FAISS 仅用于本地复现或明确配置的降级路径，不是生产主检索实现。

## 2. 为什么采用 Dense + BM25 + Reranker

电商政策同时包含口语化表达和精确术语、数字、时限。Dense 负责语义泛化，例如“买了不想要怎么办”；BM25 负责命中“七天无理由”“48 小时”“运费险”等词面；Reranker 读取问题和候选片段，进行更细粒度的相关性排序。三者分别解决召回覆盖、精确匹配和候选排序问题，不能互相替代。

中文 BM25 在建库和查询时统一使用 jieba 分词，并维护“运费险、七天无理由、极速退款、价格保护”等领域词典。IDF 用于降低常见词权重、提高业务专有词区分度。分词规则或词表变化时，必须生成新的知识版本并重新评测。

## 3. Milvus 与 Collection 设计

生产 Milvus Collection 同时保存：

| 字段 | 作用 |
|---|---|
| `dense_vector` | Embedding 语义召回 |
| `sparse_vector` | 由中文分词和 BM25 统计编码的稀疏召回 |
| `document_id`、片段内容 | 证据和去重 |
| `source`、`knowledge_version` | 引用、版本和发布审计 |
| `tenant_id`、可见范围、有效期 | 租户隔离和过滤 |

每个知识版本使用独立 Collection，采用不可变发布：文档审核后离线切分、Embedding、BM25 建库，运行固定评测、引用检查和拒答检查，预加载成功后才切换活跃版本。线上查询只命中已发布版本，默认保留最近 3 个稳定版本。

回滚是切换活跃版本指针到已经存在的旧 Collection，不需要重新切分、生成 Embedding 或重建索引；指针切换秒级生效。若应用同时进行多副本发布，应用层仍按滚动发布节奏完成。缓存键包含知识版本，因此新旧答案不会串用。

## 4. 召回、融合和精排

生产路径以 Dense Top100 和 BM25 Top100 形成候选，Milvus 在服务端按固定权重融合并去重。权重通过评测集扫描确定，当前面试口径为 Dense 0.7、BM25 0.3。再按粗排分数截断到约 Top25，避免把全部候选交给 Cross-Encoder；BGE Reranker 对 Top25 精排，最终提供 Top3 证据给生成模型。

本地 FAISS 回退路径使用 RRF 融合，两路结果按 `document_id` 合并，并进行内容前缀二次去重。该实现用于无 Milvus 环境的本地复现，不改变生产口径。

## 5. 评测口径

固定政策评测集共 100 条有答案问题：口语改写 40 条、精确政策和数字 30 条、多条件问题 20 条、易混淆政策 10 条。无答案、过期政策和越权查询作为负向集合，单独评估拒答和权限行为，不混入 Hit@3 分母。

| 方案 | Hit@3 | MRR | 说明 |
|---|---:|---:|---|
| 纯 Dense 基线 | 72% | 0.65 | 只使用语义召回 |
| Dense + BM25 + 融合 + Reranker | 91% | 0.88 | 完整生产链路 |

Hit@3 表示正确证据是否出现在前三条；MRR 表示第一条正确证据排名倒数的平均值。完整提升属于整条链路，不能把全部 19 个百分点归因于 Reranker。需要拆分贡献时，做 Dense、Dense+BM25、Dense+BM25+Reranker 三组消融。

## 6. 可信回答与引用

每个片段至少包含 `document_id`、来源、知识版本、有效期、适用角色和租户范围。回答必须能回指证据和版本，并区分：

- 实时业务事实：订单、物流、价格和库存以 MCP 返回为准。
- 当前政策：以当前活跃知识版本为准。
- LLM：只负责基于证据组织语言，不能改写数字、条件或事实。

检索到但回答仍错误时，按“召回 -> 上下文组装 -> 生成忠实度”逐层定位：先看 Hit@3/MRR，再看实际送入模型的片段，最后核对回答中的每个事实能否在证据中找到。

## 7. 知识运营闭环

```text
聊天/工单/录音等交互数据
 -> 脱敏、转写、聚类和质量筛选
 -> 候选知识 / FAQ / 关系抽取
 -> 运营、业务或法务审核
 -> 新知识版本建库
 -> 固定评测、引用和权限检查
 -> 灰度发布
 -> 观察命中率、无引用率、转人工率和反馈
 -> 持续补全知识缺口
```

LLM 只能生成候选，不能自动发布退款、售后或合规规则。图谱实体、关系和规则可以作为检索与影响分析的补充，但当前项目的核心落地能力是版本化混合检索和受控工具链，不应把未实现的图数据库写成已上线事实。

## 8. 缓存边界

Redis 语义缓存只处理稳定、低风险的政策 FAQ 和静态商品信息：政策 TTL 24 小时，静态商品信息 TTL 30 分钟。订单、物流、价格、库存和退款状态不使用普通语义缓存。缓存命中必须同时满足租户、知识版本、权限可见范围、问题类型和相似度阈值，避免相似但不等价问题串答。

固定 FAQ 对照压测中，关闭缓存组完整链路 P95 约 3.8 秒，预热缓存命中组 P95 约 0.5 秒；缓存命中跳过 LLM 调用，在约 65% 命中率下整体 Token 消耗保守估计降低约 60%。这些数字只代表固定压测口径，不代表所有客服请求。

## 9. 安全、观测与降级

- 身份从 JWT/会话服务解析，禁止以 URL `user_id` 作为可信身份来源。
- 知识查询按 `tenant_id`、角色和可见范围过滤；MCP 工具服务再次校验资源归属。
- 订单号、手机号、地址等敏感字段在日志和 Trace 中脱敏。
- Prometheus 记录延迟、P95/P99、错误、命中率和任务数；Langfuse 记录 Agent、工具、模型、版本、Token 和成本。
- Reranker 超时使用 Dense+BM25 融合结果；Milvus 不可用时拒答或转人工，不按模型记忆回答；观测系统故障不能阻塞用户请求。

## 10. 相关入口

- `RAG_data/build_index.py`：构建、发布、回滚和查看知识版本。
- `evaluation/rag_dataset.json`：100 条政策评测集。
- `evaluation/evaluate_rag.py`：Hit@3/MRR 计算及 Dense/混合对比。
- `agents/rag_milvus.py`：生产 Milvus 混合检索。
- `agents/rag_hybrid.py`：FAISS 本地回退和 RRF 融合。
- `agents/rag_reranker.py`：Reranker 精排。
- `agents/version_registry.py`：活跃版本指针。
