# 电商多智能体客服中台架构

## 1. 项目定位

本项目面向电商售前、履约与售后场景，目标是用 AI 分流高频、标准化咨询，同时把退款、投诉和其他高风险请求交给确定性服务与人工兜底。项目的技术口径来自真实业务场景设计，当前仓库提供可运行的技术原型和评测/压测工件；生产能力描述以可落地的企业架构为准，不把本地 Mock 数据误写成线上真实业务数据。

核心技术：LangGraph、FastAPI、MCP、Milvus、Redis、PostgreSQL。

核心指标口径：

- 路由准确率：固定 170 条人工标注路由集，基线 130/170=76.5%，分层路由 155/170=91.2%。复合问题的所有子任务均路由正确才算正确。
- 并行收益：典型双意图的领域任务执行阶段由串行 3.5 秒降至并行约 2.0 秒，缩短约 43%；不代表所有请求端到端缩短 43%。
- 检索质量：固定 100 条政策评测集，纯 Dense 的 Hit@3/MRR 为 72%/0.65，完整 Dense+BM25+融合+Reranker 链路为 91%/0.88。
- 缓存性能：固定 FAQ 对照压测中，关闭缓存组 P95 约 3.8 秒，预热缓存命中组 P95 约 0.5 秒；65% 命中率下 LLM Token 消耗保守估计降低约 60%。

## 2. 总体架构

```text
用户
  -> API Gateway / FastAPI
     鉴权、租户上下文、限流、输入校验、会话隔离、情绪与转人工入口
  -> Manager
     结构化拆解多意图、白名单/参数/风险校验、并行调度、结果聚合
  -> Domain Agents
     Order / Product / Logistics / Coupon / Policy 能力域
  -> MCP 工具网关
     工具 Schema、服务端授权、资源归属校验、超时、幂等、审计
  -> 业务服务、Milvus 知识库、Redis、PostgreSQL
```

### 2.1 Gateway

Gateway 是入口治理层，不让模型决定用户身份。它从 Bearer JWT 或上游身份平台解析 `tenant_id`、`user_id`、角色和可见范围，生成可信请求上下文；URL 中的 `user_id` 最多用于一致性校验，不能覆盖认证主体。

Gateway 负责请求体校验、限流、请求 ID、会话隔离、checkpoint 读写，以及负面情绪、显式投诉和显式转人工请求的入口判断。它不负责决定订单事实、执行退款、绕过权限或直接读写业务数据库。

### 2.2 Manager

Manager 是逻辑上的调度中心，但不应成为单实例单点。部署时采用无状态多副本；跨请求状态保存在 Redis checkpoint，工单、退款命令和审计事件保存在 PostgreSQL。某个实例故障后，负载均衡可将新请求转发到其他实例；正在执行的请求按最近一次 checkpoint 重试或降级。Redis、PostgreSQL 也必须采用企业级高可用方案，否则会把单点转移到共享存储。

Manager 只生成受约束的任务计划，后端随后执行 Schema、枚举、必填字段、任务数量上限、领域白名单、参数格式、去重和风险校验。模型不能直接把自然语言计划变成退款或其他写操作。

### 2.3 Domain Agent

| 能力域 | 负责内容 | 禁止事项 |
|---|---|---|
| Order | 订单查询、售后资格、退款草案 | 不直接写数据库，不绕过确认执行退款 |
| Product | 商品信息、规格、静态商品知识 | 不把实时库存/价格当作长期缓存 |
| Logistics | 物流轨迹、异常和预计送达 | 不修改物流状态 |
| Coupon | 可用券、门槛校验、优惠建议 | 不直接发券或核销 |
| Policy | 政策/SOP 检索、来源引用 | 不以模型记忆替代当前知识版本 |

Manager 对独立任务进行并行调度；每个任务有独立超时和异常结果。查询类任务可有限重试，退款等写操作不能盲目自动重试。部分任务失败时返回成功结果并明确失败领域；影响资金或资格判断的关键任务失败时停止写操作并转人工。

## 3. 四条核心设计

### 3.1 分层编排

单 Agent 面对 15+ 个领域工具时，工具选择空间、Prompt 和权限边界都会变大，多意图还容易串行执行。分层设计将入口治理、计划决策和领域执行分开，并通过任务去重、并行调度和异常隔离控制延迟与故障影响。

### 3.2 混合检索与版本

政策问题走 Dense + BM25 双路召回、融合排序和 BGE Reranker 精排，最终返回带来源和知识版本的 Top3 证据。生产后端使用 Milvus 同时承载稠密向量、BM25 稀疏向量和元数据；FAISS 仅作为本地复现或降级路径。知识版本按独立 Collection 不可变发布，先离线构建、评测和预加载，再切换活跃版本；回滚只切换已保留的旧版本指针，不重新建索引。

### 3.3 MCP 受控操作

MCP 将订单、商品、物流和优惠券能力封装为白名单工具。工具 Schema 不暴露用户身份参数，认证上下文在运行时注入，工具服务再次校验租户和资源归属。退款采用“生成草案 -> 用户确认 -> 幂等执行 -> 审计留痕”，确认令牌绑定草案、用户、订单、金额和有效期；幂等键降低重复执行风险，但不替代支付渠道和对账系统的最终一致性控制。

### 3.4 语义缓存与可观测性

Redis 语义缓存按租户、知识版本和可见范围隔离。政策 FAQ TTL 24 小时，稳定的静态商品信息 TTL 30 分钟；订单、物流、价格、库存和退款状态不做普通语义缓存。Prometheus 记录延迟、错误率、P95/P99、缓存命中率和任务数量；Langfuse 追踪 Manager、Agent、工具和模型调用，记录脱敏后的版本、Token 和成本信息。可观测系统旁路异步上报，不能阻塞主链路。

## 4. 端到端请求流程

1. FastAPI 校验请求并从认证上下文得到租户、用户和角色。
2. Gateway 检查限流、显式转人工和负面情绪，恢复 Redis checkpoint。
3. Manager 输出结构化任务计划，后端执行 Schema、白名单、参数、数量和风险校验。
4. 独立任务去重后并行调用领域 Agent；各 Agent 只能访问本领域 MCP 工具。
5. MCP 服务端注入身份并校验资源归属；Policy 使用当前知识版本进行混合检索和引用返回。
6. Manager 按权威性聚合结果：实时订单/物流事实 > 当前政策版本 > LLM 表述。冲突或关键事实缺失时追问、拒答或转人工。
7. 退款等写操作必须经用户确认和幂等执行，并写入审计事件。
8. 返回回答、来源、转人工信息或处理中状态，同时异步上报 Trace 和指标，保存 checkpoint。

## 5. 数据与部署边界

- PostgreSQL 保存租户、工单、退款命令、确认令牌和审计事件；生产订单数据由订单域服务拥有，客服中台不跨域直接写库。
- Redis 保存会话 checkpoint、语义缓存和短期状态；缓存键必须包含租户、知识版本和可见范围。
- Milvus 保存版本化稠密/稀疏索引和文档元数据；旧版本保留最近 3 个稳定版本，稳定运行后再清理。
- 当前仓库的订单、商品、物流和优惠券数据可使用 SQLite Mock 进行本地验证；这不等于生产数据存储方案。
- Docker Compose 用于本地和生产验证入口；生产部署还需要受管 PostgreSQL、Redis、Milvus、密钥管理、TLS/OIDC、限流和多副本编排。

## 6. 可靠性与降级

| 故障 | 处理 | 禁止行为 |
|---|---|---|
| 单个领域 Agent 超时 | 返回其他成功结果并说明失败领域 | 整个请求直接 500 |
| Reranker 超时 | 使用 Dense+BM25 融合排序 | 无限等待 |
| Milvus 不可用 | 政策问题拒答或转人工 | 按模型记忆编造政策 |
| MCP 查询超时 | 返回处理中/部分结果 | 写操作无条件重试 |
| Redis 不可用 | 生产实例不接流量或走明确降级 | 返回不确定的旧缓存 |
| Langfuse/Prometheus 不可用 | 异步上报失败可丢弃 | 阻塞用户请求 |
| LLM 不可用 | 有限重试后转人工 | 无限重试造成雪崩 |
