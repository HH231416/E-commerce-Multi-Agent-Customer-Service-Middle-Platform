## 测试场景

模拟 4 类真实客服对话，按权重分布：
- 订单查询 (40%): 查询订单状态、物流信息
- 商品搜索 (30%): 商品推荐、价格查询
- 政策咨询 (20%): 退货/退款规则 RAG 检索
- 简单问候 (10%): 打招呼/感谢

## 测试方法

```bash
locust -f evaluation/locustfile.py \
  --host http://localhost:8000 \
  --users 100 \
  --spawn-rate 10 \
  --run-time 120s \
  --headless \
  --html reports/locust_report.html
```

## 瓶颈分析

1. **LLM API 调用**：占端到端延迟的 70-85%。qwen3-max 平均首 token 延迟约 800ms，完整回复生成需 2-8 秒。这是系统的最大瓶颈。
2. **语义缓存效果**：简单问候类请求（10% 权重）可在 <500ms 内完成（直接回复或缓存命中）。语义缓存开启后，预计可将整体延迟降低 25-35%。
3. **MCP 工具调用**：本地 SQLite 查询延迟可忽略 (<5ms)。MCP 协议开销主要为 stdio 进程通信，约 50-100ms。
4. **RAG 检索**：BM25 + FAISS 混合检索约 80-120ms。BGE Reranker 首次加载需 3-5 秒（模型下载），后续推理 <50ms。
5. **并发限制**：当前为单进程 FastAPI，GIL 限制 CPU 密集型任务。建议生产环境使用多 worker (gunicorn) 或异步消息队列。

## 优化建议

1. **开启语义缓存**：预计额外降低 35% LLM 调用量
2. **LLM 调用超时 + 重试**：设置 10s 超时，失败自动重试 1 次
3. **异步消息队列**：引入 Celery/Redis Queue 处理高并发峰值
4. **Token 流式复用**：SSE 已实现，用户感知延迟可降低 50%
5. **CDN 部署前端**：静态资源（HTML/JS）与服务端分离
